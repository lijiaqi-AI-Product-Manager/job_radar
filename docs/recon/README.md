# 侦察顺序与规则

侦察产出是适配器会话的**唯一输入**。没有"可做"结论的侦察文档，不写适配器。

## 优先级（平台优先于大厂）

中国大量公司的校招站是挂在招聘 SaaS 上的，一个平台适配器 + yaml 一行一家公司，是扩量杠杆最大的路径。所以：

1. **第一批：招聘平台**（同时估算每个平台的租户数量，租户数量决定先做哪个）
   - Moka（`app.mokahr.com` 一类租户站）
   - 北森（Beisen / iTalent 校招站）
   - gllue
   - 大易（Dayee）等其他候选（侦察时顺带记录发现的新平台）
2. **第二批：大厂自研站**（腾讯、阿里、字节、美团、京东、百度、网易、小米、华为…），放在平台适配器跑通之后；同样必须先侦察。
3. **公开聚合渠道作补充**：用户已授权合规聚合补源，逐站核验 robots、条款、归属与内容使用边界，显式标 `source_kind: aggregator`，与官方分口径。线索发现不能直接算覆盖；未经许可的转载、验证码、登录或签名入口仍不做。

## 同时要验证的一件事

GitHub Actions 的海外机房能否正常访问这些站点（状态码、耗时、返回内容是否一致）。用 `.github/workflows/recon-probe.yml` 手动触发，结果写进各侦察文档第 7 节。**如果大面积不可达，整个"零成本"方案要重新评估，立即告诉用户。**

## 规则

- 每个站点 ≲20 次请求，间隔 ≥1 秒，只读公开页面。
- 遇到验证码/账号登录/签名 → `blocked`，不尝试绕过。
- 站点对匿名访客下发的会话 cookie / 页面内嵌 token，按浏览器正常顺序使用是允许的（2026-10-21 起，见 docs/DEVELOPMENT.md 铁律 1）；
  侦察时用 `FLOW` 验证，用 `RENDER`（浏览器渲染）查看前端渲染页面的文字和它请求的接口。
- 条款与 robots 要引用原文要点，不要概括成"没问题"。
- 文件命名：`docs/recon/<name>.md`，样本放 `docs/recon/samples/<name>/`。
