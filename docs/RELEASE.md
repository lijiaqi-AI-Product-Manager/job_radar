# 发布检查与数据库兼容

代码回归、数据质量与覆盖目标分别验收。源码检查通过不能代替真实快照检查，也不能证明覆盖率已经达到目标。

## 常规检查

```bash
uv run ruff check .
uv run pytest
uv run python scripts/check_docs_links.py
uv run python scripts/check_compliance.py
uv run python scripts/coverage_report.py --json
uv run python scripts/release_check.py --home <数据目录>
```

真实数据目录需含 `jobs.db`、`jd_text.db` 与 `calendar.db`；缺少数据的 SKIP 不算通过。80% 覆盖独立运行 `scripts/coverage_report.py --json --min-coverage 0.8`，当前启用配置为944/1,655（57.04%，2026-11-05复算），预期退出1，仍差380家。

## 日历定点修正

已审核的截止日撤回清单位于 `calendar/corrections/`。先在下载副本上预演，再加 `--apply`：

```bash
uv run python scripts/apply_calendar_corrections.py --db calendar.db
uv run python scripts/apply_calendar_corrections.py --db calendar.db --apply
```

该工具只撤回清单中旧的人工日期，保留原链接与观测时间；不会覆盖后续重新核实的数据，重复执行不再改动。
`calendar-data-repair` 手动工作流会备份旧日历、修正 GitHub `data-latest` 的日历与压缩包；
它与每日采集共享发布锁，完成后触发国内镜像同步，不重新采集或发布软件包。

## 既有质量门禁

完整读取成功但云端未能复验的来源，可使用手动 `verified-source-recovery` 工作流恢复。输入必须来自相同版本的适配器、固定访问守卫和源限速；登录、验证码、明确禁止读取或不完整分页均不适用。传输文件仅包含脱敏后的标准化岗位与实际观测时间，不包含会话值或原始响应，不提交到 Git。

工作流按本仓库附件ID和SHA-256获取有界输入，验证源配置摘要、主体、类型、链接域名、日期及24小时有效期。较新观测不能被旧结果覆盖；既有骤降保护继续生效，任一源拒收则整批不写入。旧三库先备份，重新构建日历、兼容导出并通过真实数据门禁后，才成套切换公开快照。作业与每日采集共用发布锁；观测时间不会改成导入时间。

`daily-crawl` 的默认单源预算为3600秒，整轮仍限14400秒。特变电工已有1672条校招与社招记录，逐岗读取详情在1请求/秒下无法在旧900秒预算内完成；延长单源预算让大源有机会完整刷新。手动复验可调整 `source_budget_seconds`，限速、分页范围、整轮上限和失败保留旧岗位的规则继续生效。

全量采集后另有默认1800秒、最多3600秒的补采窗口，只处理预算未完成及明确的连接故障、429、5xx；原单源预算扣除已用时间，不在补采时重置。实习僧按真实共用域名排队，避免多个关键词来源占满工作线程。补采优先读取历史耗时较短的来源，每个来源最多再尝试一次；访问许可错误、解析异常与保护性拒收不自动重试，不放宽空结果或骤降保护。

需要单独补采时，可在 `daily-crawl` 的手动运行中勾选 `recovery_only`，保持 `only_sources` 为空、`stale_only_hours` 为0，并设置 `recovery_budget_seconds`。流程从已核验的三库快照恢复最近观测，仅抓取符合上述条件的来源；其他来源保留自己的观测时间，不能声称本次重抓过全部来源。后续仍经过日历构建、兼容导出和质量门禁才发布。

`data-health` 使用同一条带标记的问题持续更新；完整来源集合均正常、观测未超过24小时且流水线成功时关闭，复发时重新打开同一条。定向或按未更新时长筛选的局部采集不能覆盖全量健康摘要，也不能关闭全量健康问题。每次运行保存首次摘要、补采结果、最终摘要和报告14天，便于核对实际恢复数；报告缺失或流程取消均视为未确认恢复。站点访问限制或结构变化仍需核实处理，不能用关闭 Issue 代替修复。

补采指标分别记录排队、实际启动、未启动和恢复数。整轮预算结束时尚未启动的来源可能仍被编排器记为预算未完成，必须依据新增运行记录的正耗时确认启动，不能把排队数量报告为实际读取数量；历史版本摘要只展示排队与恢复数。

门槛定义于 `scripts/release_check.py`，不因文档或界面更新而放宽。

发布检查还会以只读连接执行8种首页及技能中的去重命令示例。查询类示例必须有结果，帮助、更新与采集命令仅校验参数，不在此步骤联网或写库；岗位ID取快照现有记录，日期占位符以当天或当月末展开。详细结果可运行 `python scripts/check_readme_examples.py --home <数据目录>` 查看。安装后的wheel另外验证固定职类词表及“财务”别名在旧原值存在时仍可召回。

## 公开数据库兼容

日历工作库为 schema 2，字段证据保存在独立的 `entry_field_evidence` 表。
公开导出继续标记 calendar schema 1，保留可忽略的证据表；旧客户端读取原表，
新客户端可幂等升级并读取字段证据。 客户端读取后的本地日历可为schema 2；公开格式核验使用已校验的压缩分发附件。每日与修正发布均先兼容导出再上传。

主分支工作库为 jobs schema 3 / text schema 2，包含本地 FTS5 索引。既有已发布客户端只能读取 jobs 2 / text 1；因此每日发布先生成独立的兼容副本：

```bash
uv run python scripts/export_public_databases.py --home data --out data/public
```

导出使用 SQLite backup 读取工作库副本，去掉可重建的全文索引和相应触发器，恢复公开版本号，执行 VACUUM 与完整性检查，再原子替换输出。岗位、正文与业务事件保留；工作库不改变。未知 schema 拒绝导出，不能静默降级。

`daily.yml` 在日历构建、兼容导出和真实质量门禁成功后，上传三库的不可变压缩文件，再原子更新 Release 中的完整性清单。旧文件名继续供历史客户端读取。新版客户端使用清单中的同一代三库；2.1.0 默认直接查询兼容快照，已有全文索引时复用。`update --prepare-index` 可在新快照中准备索引，完成后才切换；准备失败保留原快照。

本地更新使用 `JOBRADAR_HOME/snapshots/<代号>/` 存放成套三库，验证完成后原子切换 `.active.json`。CLI/MCP 的一次查询固定同一代；失败不覆盖已有数据，`doctor` 输出实际 `data_dir`。国内镜像先暂存完整分片，匿名校验每片及整文件的 SHA-256，再切换稳定入口；失败保留上一代。

## 版本发布

1. 更新 CHANGELOG，记录真实数据检查与独立覆盖结果。
2. 构建 wheel / sdist，确认 sdist 小于 5 MiB，没有缓存、数据库或凭据。
3. 独立环境安装 wheel，验证 CLI / MCP、迁移和包内公司简称映射。
4. 按授权范围提交和推送；GitHub 代码推送、版本 tag、数据 Release 与 PyPI 发布分别处理。
5. 版本唯一来源为 `src/jobradar/__init__.py`。正式发布按 [PyPI 流程](PUBLISHING.md)，完成后验证真实安装、下载与增量更新。

缺失日期、城市、届次或学历保留为空。离线检查不能替代逐站访问规则与当前产出的核实。

## 正文观测与增量读取

岗位列表与正文分别记录观测时间。大易来源复用正文时不刷新原正文时间，新岗位或标题、招聘类型、发布日期、学历变化时读取详情；最多168小时后要求重读。列表始终完整读取，异常分页或列表失败不能使用缓存冒充成功。详情及统计口径见 [岗位与正文的观测时间](FRESHNESS.md)。

## 详情进度交接

本地按同一套公开访问守卫完整或部分读取的详情，可以交给云端的定向复验继续使用：

```bash
python scripts/detail_progress.py export --cache-root data/detail-cache --only SOURCE_ID --out detail-progress.json.gz
```

导出只包含标准化岗位正文、原读取时间与来源/适配器签名，不包含请求参数、会话值或原始响应。文件不提交Git。将文件上传本仓库的临时Release附件后，在`daily-crawl`手动运行中填写附件ID、打印的SHA-256及相同的`only_sources`，保持`recovery_only=false`和`stale_only_hours=0`。

云端先核对本仓库附件、摘要、解压容量、来源、雇主、适配器版本与原详情时效，再合并进度；较新的已有正文保留。采集仍重新读取完整列表并执行访问、归属、分页和入库检查，进度导入本身不会改变岗位、事件或来源健康状态。失败或未完成的来源继续保留旧岗位；只有实际完整读取成功才计为恢复。

每日采集和手动修正发布会在日历构建前统一已有岗位职类，生成保留原值的分类审计计划。存在修正时，运行附件保留计划及结果90天；计划本身不表示整套快照已经发布成功，仍需核对后续门禁和发布步骤。此维护不创建招聘变更事件，也不刷新岗位状态或观测时间。

发布数据结构门禁同时检查固定职类大类和子类的规范配对，平台行业原值或不规范组合会阻止发布；缺失分类仍允许留空。

详情进度签名统一适配器源码的LF/CRLF换行，兼容同一源码的既有签名；实质代码或来源参数变化仍使旧进度失效。较新的已有详情不会被较旧交接结果覆盖。
