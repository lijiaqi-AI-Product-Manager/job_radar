# 常见问题（FAQ）

## 数据相关

**Q：为什么有些公司在日历里，但搜不到岗位？**

日历覆盖 494/500 家（其余 6 家不可合规覆盖），但**能抓到岗位级数据的是 161 家**。
剩下的公司要么是自研招聘站（每家接口不同，需要一家一家适配）、要么是加密平台
（Moka / 飞书 ATSX，页面能看、接口加密）。对这些公司，日历仍会给出
届次、项目类型、方向、城市、投递入口和来源，并在 JD 被挡时附一句
`{公司名}希望你去他们的招聘页逛一逛哦~`。

**Q：数据多久更新一次？**

每天 UTC 19:17（北京时间 03:17）自动采集并发布新 Release；每周一额外打一个归档快照。
Gitee 镜像同日同步，通常比 GitHub 晚 30~60 分钟。

这是整体任务的调度频率，不保证每个来源每天成功刷新。预算、限速、访问限制或保护性拒收
都可能让部分来源继续保留旧记录；整体 `data_as_of` 较新也不能证明所有岗位状态都是今天的。
`jobradar doctor` 的 `source_health` 会统计超过 48 小时未成功刷新的来源及其保留岗位数，
最多列出 20 个来源；用 `jobradar sources --problems` 查看完整清单，投递前打开岗位原链接确认。

**Q：为什么 `jobradar update` 有时秒回、有时要下载 55MB？**

默认是**增量更新**：先比对 Release 里各文件的 sha256，没变就跳过。
`--force` 可以强制全量重下。

**Q：为什么某些岗位没有 JD 原文？**

数据集只收「能拿到职责/要求原文」的岗位（当前在招岗位里 99.8% 有正文）。
某些大厂的 JD 接口有滑块/签名/登录墙，这类公司只发日历信息，不硬凑正文。

**Q：岗位下架是怎么判定的？**

连续 3 次成功抓取都没再出现才标记为下架。**抓取失败不会导致下架**
（防止一次网络故障把几万个岗位误删）。

**Q：过期岗位和日历批次需要每天手动清理吗？**

不需要。默认搜索和日历查询按北京时间自动隐藏明确截止日已过的记录，截止当天仍保留，次日零点起隐藏。
即使本地暂未下载新快照，也按查询当天判断；历史记录和证据继续保留，不会物理删除。
岗位历史用 `search --include-closed`，日历历史用 `calendar --include-expired`；
`calendar --open-on YYYY-MM-DD` 则按指定日期回查，不受今天已过期的限制。

源成功抓取时仍按既有规则维护岗位下架事件。缺少截止日、抓取失败、超时或保护性拒收，都不作为自动关闭依据；
高校公告展示过期日也不能当企业截止日。旧来源的新鲜度问题由 `doctor` 与 `sources --problems` 提示。

日历的 `deadline_scope=batch` 才表示批次截止；`job_evidence` 表示日期来自岗位样本，
最早一个岗位到期不能证明整个批次结束，这类条目不会因此整批隐藏，开放状态仍标为未知。

**Q：网申时间为什么很多是空的？**

1372 条日历里只有 8 条（0.6%；纯人工条目 1.8%）带完整网申起止——官网大多只写「9 月起」。公众号推文通常有，
但微信对数据中心 IP 会返回验证页，按合规要求不绕过，所以留空而不是编造。

## 使用相关

**Q：装完却不支持参数，或 `search --help` 报错？**

先核对实际 Python 环境与安装来源，按 [安装指南](INSTALLATION.md) 升级到经过验证的版本，
安装或升级后确认帮助中有 `calendar --city`、`calendar --include-expired` 和 `search --deadline-before`。
终端与 MCP 若使用不同环境，需要在实际运行的那个环境中安装。

**Q：首次查询为什么很慢，网络盘怎么办？**

兼容快照不包含全文索引。普通公司、城市查询及 `show`、`stats`、`doctor` 不再自动重建全文索引；
首次对至少 3 个字符的词做 `--text` 搜索时才按需构建，之后复用。构建耗时取决于本地磁盘，
网络文件系统可能明显更慢；优先把 `JOBRADAR_HOME` 放在本地 SSD。

如果不希望构建索引，在启动 CLI 或 MCP 前设置 `JOBRADAR_BUILD_SEARCH_INDEX=0`。
这会阻止补建索引，并回退到兼容的全文扫描，搜索语义不变，但全文查询可能更慢。
已经存在的索引仍可复用；数据包体积不会因此减小。

**Q：`--company 京东` 为什么返回 0 条？明明库里有「京东方」**

因为京东和京东方是两家公司。京东的岗位从它自己的校招站 `campus.jd.com` 采（2026-10-26 起 355 条），与京东方无关。
`--company` 的匹配顺序是：公司名全等 → 简称表（`中核`→中国核工业集团）→
**唯一**子串（`阿里`→阿里巴巴）。子串只差一个字的前缀延伸不算命中
（`京东` 只差「方」一个字，属于典型的张冠李戴），这时会返回 0 条并给出提示：

```json
"company_match": {"match": "none", "matched": [], "candidates": ["京东方"]}
```

要看「所有名字里带 X 的公司」，显式加 `--contains`（如 `--company 中国 --contains`）。
命中多家时 `match` 为 `ambiguous`、同样不返回数据——**宁可说没有，也不把别家的岗位当成本家的**。

**Q：结果为空，是不是说明这家公司没在招？**

不是。先看返回里的 `hints` 和 `company_match`：
- `company_match.match = none/ambiguous` → 名字没对上，换完整公司名再查；
- `hints` 里有「`--grad-year` 只命中写了届别的岗位」→ 去掉该过滤再查一次
  （届别/城市/职类是从标题和 JD 原文里按规则提取的，很多岗位两处都不写）；
- 都没有才说明「这批数据里没有它的在招岗位」，而不是「它没在招」。

**Q：`compare` 的 `not_found` 是公司没收录吗？**

它表示本次筛选没有返回岗位，可能只是该公司没有符合职类、标题或全文条件的记录。
查看 `missing_companies`（未收录）、`no_matching_jobs`（已收录但筛选无结果）和
`ambiguous_companies`（名称需要澄清）；`company_matches` 给出具体匹配方式与候选。

对比支持 `--city`、`--type`、`--grad-year`，对所有公司应用同样的严格条件。
搜索返回 `empty_reason` 与 `company_coverage` 区分未收录、没有当前岗位和筛选无匹配；
`total` 是筛选总数，`returned` 是返回数，`truncated` 表示是否只返回了部分样本。

**Q：异常下载会覆盖原来的数据库吗？**

下载先核验实际字节与发布摘要，再校验 SQLite 文件头、必需表与完整性；校验失败保留原库。
已有岗位库还会检查记录数和观测时间不倒退。旧版没有验证来源的摘要缓存会重新核验，
只有与实际下载字节匹配的摘要才用于后续跳过下载；强制更新也不会跳过摘要检查。

**Q：需要 API key 吗？**

不需要。数据是公开的 Release 资产，匿名即可下载；查询完全在本地 SQLite 上跑。
设置 `GITHUB_TOKEN` 只是提高 GitHub API 限额（增量更新用一次调用）。

**Q：国内下载慢怎么办？**

```bash
jobradar update --mirror gitee      # 或 export JOBRADAR_MIRROR=gitee
```
Gitee 上的大文件是分片存放的（`.partNN`），客户端会自动下载并合并；失败自动回退 GitHub。
也可以把 `JOBRADAR_MIRROR` 设成任意 GitHub 加速前缀（如 `https://ghproxy.example/`）。

**Q：怎么让 AI agent 用上？**

- CLI 集成：参考 `skill/jobradar/` 中的查询工作流
- 支持 MCP 的客户端：命令填 `jobradar-mcp`（stdio）
- 直接当库：`from jobradar.core import queries`

**Q：数据可以商用/二次分发吗？**

代码 MIT。数据是各公司官网的公开岗位信息，请自行评估目标站点的条款；
本项目只做聚合与结构化，不代替官方投递渠道。

## 开发相关

**Q：怎么加一家公司？**

先侦察（`docs/recon/`），再按 `docs/DEVELOPMENT.md` 的适配器流程做；北森/大易/Workday 只需在
`sources/*.yaml` 加一行。详见 [CONTRIBUTING.md](../CONTRIBUTING.md)。

**Q：改了查询逻辑怎么确认没变差？**

`evals/` 里有固定的问题集和期望答案，`uv run python -m pytest` 之外可按
[evals/README.md](../evals/README.md) 跑一遍对照。

**Q：Windows 上要注意什么？**

本项目在 Windows 上跑全量测试（CI 有 windows-latest）。
非中文 locale 的控制台也已处理（CLI 会把输出切到 UTF-8）。

**Q：本地数据坏了（磁盘错误、下载被中断）怎么办？**

`jobradar doctor` 会显示 `jobs_db: false` 并给出建议。直接跑：

```bash
jobradar update --force     # 全量重下，覆盖坏文件
```

`update` 本身也会自愈：增量比对时如果发现本地库打不开（`PRAGMA quick_check` 失败），
会跳过「已是最新」的判断、重新下载那个库。

**Q：Gitee 镜像同步到一半（分片不全）会怎样？**

客户端会先试整文件、再试 `.partNN`；拼接出来的文件要过 gzip + SQLite `quick_check`，
不完整就自动退回下一个镜像（GitHub）。镜像工作流本身也有大小校验，不会把半成品当成功。
