> 本报告覆盖两轮：10-25 的平台穷举（得出 122 家可做），10-26 的建源落地 + 日历证据打通。

**这轮最关键的一件事不是「又加了几家公司」，而是「已经抓到的数据有没有真的变成产品」。**
10-25 时 `sources/` 只覆盖 272 家公司，而侦察早已实测打通 122 个租户 —— 其中 91 家
「已验证可抓但从来没建过源」。同一时期，热招（大易）接口每个岗位都自带城市和截止日，
但这些字段只落在 `jobs.db` 里，日历一条都用不上。**这两处都是「有数据、没产品」的漏损**，
本轮把两处都堵上了。

## 1. 本轮做的四件事

### 1.1 把「已验证可抓」的 91 家真正建源（`work/add_missing_sources.py`）

交集算法：`sample_stats_all.jsonl` 里 `normalized>0 且 jd_rate≥0.9` 的租户
− `sources/` 已有的 (adapter, tenant) − `targets` 的 blocked 名单 − ATS 厂商自身域名。

结果：`beisen.yaml` +75、`beisen_legacy.yaml` +8、`hotjob.yaml` +8，共 **+91**。
按 (adapter, tenant) 而非公司名去重——同一家公司可能挂两个租户（`changan` / `changanqiche`
都是真源），按名字去重会把其中一个误删。

### 1.2 结构化职位证据进日历（`export_job_evidence` + `--evidence-out`）

```
jobs.db（97,607 条在招职位）
  └─ export_job_evidence()  → work/ats_evidence.jsonl（305 家）
        cities_by_type  {"campus": ["长沙","北京",...], "social": [...]}
        ends_by_type    {"campus": ["2026-11-30", ...]}
        starts_by_type  {"campus": ["2026-10-15", ...]}
        grad_years      [2027]
  └─ work/build_calendar.py 作为 E0 路证据合并（权重高于正文正则）
```

**效果（可复现对比）**：

| 指标 | 接入前 | 接入后 |
|---|---|---|
| 校园岗城市覆盖率（数据层） | 0.6% | **29.8%** |
| 日历条目带城市 | 547 | **624** |
| 日历条目带届次 | 616 | **670** |
| 日历条目总数 | 1,326 | **1,337** |

城市按 `recruit_type` 分桶后再回填：社招岗的城市绝不会串进校招条目。
批次自己没有城市证据时，先看「同招聘类型的城市」，再看「全公司并集（仅单一批次时）」，
顺序不能反——反过来会让春招条目带上秋招分公司的城市。

### 1.3 日历「来源」列终于有日期

1,326 条条目的 `source.date` 原本**全部为 null**。用户看到「来源：某校就业网」却不知是哪天
的公告，无法判断时效。现在按批次收集该批次自己那批公告的 `publish`，倒序取最新，
覆盖 **308 条**。规则上严格禁止拿 `as_of` 或别的批次的日期冒充。

### 1.4 合并 7 对重复主体（`work/merge_duplicate_targets.py`）

| 被合并 | 保留 | 原因 |
|---|---|---|
| ABB（外资在华） | ABB中国（新能源与先进制造） | 「ABB」是外资泛称，ABB中国才是运营实体 |
| 宝洁中国（扩展池） | 宝洁（快消与零售） | 扩展池是采集副产物，不是人工选定名单 |
| 微软中国（扩展池） | 微软（外资在华） | 同上 |
| 西门子中国（扩展池） | 西门子（外资在华） | 同上 |
| 阿斯利康中国（扩展池） | 阿斯利康（外资在华） | 同上 |
| 民生银行（银行） | 中国民生银行（银行） | 后者是工商登记全称 |
| SAP（外资在华） | SAP中国（企业服务） | 后者行业标注更具体 |

不合并的代价：**同一家公司在行业分布里被算两次**，日历被拆成两个 group
（用户在「ABB」下只看得到半条，另一半挂在「ABB中国」下）。
合并后 1,021 → 1,014 家，被合并名进 `aliases`，`match_targets` 仍能双向命中。

## 3. 踩到的坑（含假阳性纠正）

1. **`careers.iqiyi.com` 被误判给 6 家不相干公司**。ATS 指纹扫描只认 URL 模式，不看归属。
   后来加「回读站点 title + 岗位 company 字段」的同名核对，丢弃 **17 只 beisen 假阳性
   + 5 只 hotjob 假阳性**。
2. **大易门户根页是 JS 空壳**（3.5KB iframe）。真租户 ID 藏在
   `POST /wecruit/common/getSLD` 的 `linkData.link` 里。第一版验证脚本因此把 30 个候选全判失败。
3. **北森「租户不存在」返回 200 + 1,228 字节 "Not Found" 页面**，不是 404。
   加体积/标题剪枝后单家耗时从 ~280s 降到 ~1.5s。
4. **`CategoryId` 是站点自定义的**，不是全局枚举（茶颜悦色用 8/9/11–14，来伊份用 1/4）。
   所以「Count>0 但归一化=0」会成片出现，必须采样验证。
5. **`3000-01-01` 是长期开放的哨兵值**，不是真日期。不归一的话「找快截止的岗位」
   会筛出一堆 3000 年。
6. **北森新版门户不返回城市与截止日**（本轮定量确认）：扫完全部 251 个租户 × 30 条，
   `LocNames` 恒 `[]`、`LocID` 恒 `null`、`EndTime`/`PostDate` 恒 `0001-01-01`。
   这是平台限制，不是代码缺陷。
7. **`source.date` 全为 null** —— 生成器写死了 `None`，等于「来源」这一列只有名字没有时间。
8. **7 对重复主体**（见 1.4），其中 3 对的两个写法分属不同行业，行业分布统计直接失真。
9. **`campus_city_ratio` 分母含社招/实习**，把指标稀释到 0.6%，掩盖了真实情况
   （只看校园岗是 29.8%）。

## 5. 复现命令

```bash

    --jobs /tmp/fullcrawl/jobs.db --out /tmp/jr/calendar.db --entries calendar/entries
```

`sources/beisen.yaml` 比对，得出 **138 个从未配置过的租户**。逐个 `POST /api/Jobad/GetJobAdPageList`

写入后按 `--only` 只抓这 89 个源，**89 ok / 0 not ok**，新增岗位 **40,283 条**，

单笔最大的几家：我爱我家 28,892、希尔顿中国 1,989、信达生物 1,241、闻泰科技 1,216、

### 这一批对日历的真实作用（要做减法）

岗位数 +37.5%，但**日历字段几乎没有提升**：

| 指标 | 抓之前 | 抓之后 |
|---|---|---|
| 日历条目 | 2,139 | **2,260**（+121，全部是新增公司的自动条目） |
| 人工条目 `jd_company` | 418 (28.4%) | **510 (34.6%)**（+92，新公司让更多简章"落到数据层"上） |
| 人工条目 `cities` | 706 (47.9%) | **719 (48.8%)** |
| 人工条目 `grad_year` | 664 (45.0%) | **666 (45.2%)** |
| 人工条目 `apply_start` | 65 (4.4%) | **65 (4.4%)**（没变） |

原因非常明确：**北森新版门户的列表接口不返回城市、发布日期、截止日**
（`LocNames` 恒 `[]`、`PostDate`/`EndTime` 恒 `0001-01-01`），而北森占数据层的 **83.6%**
（123,607 / 147,844）。所以「多抓北森 = 多岗位」但「≠ 多日期」。

### 由此确定的下一阶段优先级

`apply_start`（网申开始）只有 4.4%，是十项字段里最差的。它的原料是**发布日期**，
而发布日期只来自两类源：

1. **大易（hotjob）**：列表接口直接给 `publishDate` + `endDate`，实测 2,913 岗里
   `publish_at` 99.9%、`apply_end` 92.4% —— 是唯一「一抓就有日期」的平台。
2. **自研站 / 其他 ATS 的发布字段**：字节、美团、阿里、百度、京东、蔚来、小鹏、网易都已 100%。

结论：**再堆北森对日历是边际收益递减的**，后续增量应优先给大易加租户、给自研站写适配器。
